## はじめに

前回・前々回で、PDF仕様書（ISO 32000-2）をLLMが構造的に参照できるMCPサーバー **pdf-spec-mcp** を紹介しました。

- [PDF仕様書をLLMが「引ける」MCPサーバーを作った](https://zenn.dev/shuji_bonji/articles/ab30e8318d8be9)
- [MCPサーバー間連携でPDF仕様書を用語統一して日本語翻訳する](https://zenn.dev/shuji_bonji/articles/08fc816aabfbd8)

pdf-spec-mcp は「**仕様書を引く**」ツールでした。今回は「**実際のPDFファイルの内部構造を読み解く**」ツールです。

https://github.com/shuji-bonji/pdf-reader-mcp

### 既存のPDF系MCPサーバーの限界

npm で `pdf mcp` と検索すると、PDF系MCPサーバーはいくつか見つかります。しかし、そのほとんどは pdfjs-dist や poppler のテキスト抽出をラップしただけの薄いラッパーです。

「このPDFのテキストを出して」はできます。でも、こういう質問には答えられません。

- 「このPDFのタグ構造はPDF/UAに準拠しているか？」
- 「カタログ辞書にどんなエントリがあるか？」
- 「埋め込みフォントはサブセット化されているか？」
- 「電子署名フィールドの構造はどうなっているか？」
- 「2つのPDFの構造的な差分は？」

これらはPDFの**内部構造**に踏み込まないと答えられない問いです。

### pdf-reader-mcp とは

PDF内部構造解析に特化したMCP（Model Context Protocol）サーバーです。**15のツール**を3つのTierに分けて提供し、テキスト抽出から構造解析、仕様適合検証までをカバーします。
```
┌─────────────────────────────────────────┐
│         AI Agent（Claude等）             │
│  「このPDFはPDF/UAに準拠しているか？」       │
└──────────────┬──────────────────────────┘
               │ MCP Tool Call
               ▼
┌─────────────────────────────────────────┐
│          pdf-reader-mcp                 │
│                                         │
│  Tier 1: 基本操作（7ツール）               │
│    テキスト抽出・検索・画像・メタデータ       │
│                                         │
│  Tier 2: 構造解析（5ツール）               │
│    カタログ・タグ・フォント・注釈・署名       │
│                                         │
│  Tier 3: 検証・分析（3ツール）             │
│    PDF/UA検証・メタデータ検証・構造比較      │
└──────────────┬──────────────────────────┘
               │ 構造化された分析結果
               ▼
┌─────────────────────────────────────────┐
│           任意のPDFファイル               │
└─────────────────────────────────────────┘
```

| 比較項目 | 汎用 PDF リーダー系 MCP | pdf-reader-mcp |
| --- | --- | --- |
| 対象 | 任意のPDFファイル | 同左 |
| テキスト抽出 | ✅ | ✅（Y座標ベースの読み順保持） |
| 内部構造解析 | ❌ | ✅ カタログ辞書・オブジェクト統計 |
| タグツリー解析 | ❌ | ✅ Tagged PDF の構造可視化 |
| フォント解析 | ❌ | ✅ 埋め込み/サブセット判定 |
| 電子署名解析 | ❌ | ✅ 署名フィールド構造 |
| 仕様適合検証 | ❌ | ✅ PDF/UA・メタデータ検証 |
| 構造比較 | ❌ | ✅ 2つのPDFの差分比較 |

## 15のツール

### Tier 1: 基本操作（7ツール）

日常的なPDF操作をカバーする基本ツール群です。

| ツール | 説明 |
| --- | --- |
| `get_page_count` | ページ数の軽量取得 |
| `get_metadata` | メタデータ抽出（タイトル、著者、PDF版、タグ有無等） |
| `read_text` | テキスト抽出（Y座標ベースの読み順保持） |
| `search_text` | 全文検索（前後コンテキスト付き） |
| `read_images` | 画像抽出（base64、メタデータ付き） |
| `read_url` | URLからリモートPDFを取得して処理 |
| `summarize` | 全体概要レポート（メタデータ + テキスト + 画像数） |

`summarize` は、LLMがまず「このPDFは何か」を把握するための入口になります。

```
summarize({ file_path: "/path/to/document.pdf" })

→ | Property     | Value                |
  | Pages        | 42                   |
  | PDF Version  | 2.0                  |
  | Tagged       | Yes                  |
  | Signatures   | No                   |
  | Images       | 15                   |
  | Text Preview | This document is...  |
```

### Tier 2: 構造解析（5ツール）

ここから他のPDF MCPサーバーにはない領域に入ります。

| ツール | 説明 |
| --- | --- |
| `inspect_structure` | オブジェクトツリー・カタログ辞書の解析 |
| `inspect_tags` | Tagged PDF のタグツリー可視化 |
| `inspect_fonts` | フォント一覧（埋め込み/サブセット/Type判定） |
| `inspect_annotations` | 注釈一覧（タイプ別分類） |
| `inspect_signatures` | 電子署名フィールドの構造解析 |

#### `inspect_structure` — カタログ辞書を覗く

PDFファイルの「目次」にあたるカタログ辞書を解析します。どんなエントリが存在するか、オブジェクトは何個あるか、ストリームは何本か — PDFの全体像を構造的に把握できます。
```
inspect_structure({ file_path: "/path/to/document.pdf" })

→ Catalog Entries:
  | Key      | Type      | Value           |
  | Type     | name      | /Catalog        |
  | Pages    | ref       | 2 0 R           |
  | Metadata | ref       | 15 0 R          |
  | MarkInfo | dict      | {Marked: true}  |

  Object Statistics:
  | Total Objects | 26  |
  | Streams       | 8   |
```

#### `inspect_fonts` — フォント埋め込みを確認する

フォントの埋め込み状況を一覧化します。PDFをWebで配信するとき、フォントが埋め込まれていないと環境によって表示が崩れます。サブセット化されていれば必要な文字だけが含まれ、ファイルサイズが小さくなります。
```
inspect_fonts({ file_path: "/path/to/document.pdf" })

→ | Name                    | Type     | Embedded | Subset | Pages |
  | Helvetica               | Type1    | No       | No     | 1,2,3 |
  | BCDFGH+ArialMT          | TrueType | Yes      | Yes    | 1,2   |
  | TimesNewRomanPSMT       | TrueType | Yes      | No     | 3     |
```

`BCDFGH+` のようなプレフィックスはサブセット化の証拠です。埋め込みフォントにのみ付与され、6文字のランダムな大文字 + `+` + フォント名という形式になります。

#### `inspect_signatures` — 電子署名フィールドの構造

筆者は電子署名ソフトの開発に携わっていた経験があり、署名フィールドの構造を調べる必要が頻繁にありました。このツールは AcroForm ベースの署名フィールドを解析し、`/ByteRange`、`/Filter`、`/SubFilter`、署名理由（`/Reason`）などを構造的に返します。

```
inspect_signatures({ file_path: "/path/to/signed.pdf" })

→ | Field        | Signature1            |
  | Filter       | Adobe.PPKLite         |
  | SubFilter    | adbe.pkcs7.detached   |
  | Reason       | Approved              |
  | ByteRange    | [0, 1234, 5678, 9012] |
  | HasContents  | Yes                   |
```

### Tier 3: 検証・分析（3ツール）

Tier 1, 2 で得た情報をもとに、PDFの品質を検証するツール群です。

| ツール | 説明 |
| --- | --- |
| `validate_tagged` | PDF/UA タグ構造の検証（8項目チェック） |
| `validate_metadata` | メタデータの仕様適合チェック（10項目チェック） |
| `compare_structure` | 2つのPDFの構造差分比較（プロパティ＋フォント） |

#### `validate_tagged` — PDF/UA準拠チェック

Tagged PDFの構造が適切かを8項目でチェックします。アクセシビリティ対応が求められるPDFの品質確認に使えます。
```
validate_tagged({ file_path: "/path/to/document.pdf" })

→ ✅ [TAG-001] Document is marked as tagged
  ✅ [TAG-002] Structure tree root exists
  ✅ [TAG-003] All pages have structure content
  ⚠️ [TAG-004] Heading hierarchy has gaps: H1, H3
  ❌ [TAG-005] Document has 3 image(s) but no Figure tags
  ✅ [TAG-006] No empty tags found
  ✅ [TAG-007] Document language is set: en-US
  ✅ [TAG-008] Title is marked in metadata
```

見出しレベルの飛び（H1→H3）や、画像に Figure タグが付いていないことなど、PDF/UA 準拠に必要な問題点を具体的に指摘します。

#### `compare_structure` — 構造差分比較

2つのPDFの構造的な違いを比較します。修正前後のPDFを渡せば、何が変わったかを一覧で確認できます。
```
compare_structure({
  file_path_1: "/path/to/v1.pdf",
  file_path_2: "/path/to/v2.pdf"
})

→ | Property    | File 1 | File 2 | Match |
  | Page Count  | 10     | 12     | ❌    |
  | PDF Version | 1.7    | 2.0    | ❌    |
  | Tagged      | true   | true   | ✅    |
  | Encrypted   | false  | false  | ✅    |

  Font Differences:
  | Only in File 1    | Only in File 2       |
  | Helvetica         | BCDFGH+ArialMT       |
```

## 技術的な設計判断

### pdfjs-dist と pdf-lib の使い分け

pdf-reader-mcp では2つのPDFライブラリを併用しています。
```
                 pdf-reader-mcp
                       │
          ┌────────────┼────────────┐
          ▼                         ▼
    pdfjs-dist                   pdf-lib
   （Mozilla製）              （pdf-lib 製）
          │                         │
  Tier 1: テキスト・画像      Tier 2: 低レベル構造
  ・getTextContent()         ・カタログ辞書の走査
  ・getOperatorList()        ・オブジェクト統計
  ・getAnnotations()         ・AcroForm 解析
  ・getStructTree()          ・暗号化検出
```

| ライブラリ | 役割 | ライセンス |
| --- | --- | --- |
| pdfjs-dist | テキスト抽出、画像カウント、タグツリー、注釈 | Apache-2.0 |
| pdf-lib | カタログ辞書・オブジェクトツリー・AcroForm解析 | MIT |

なぜ2つ必要なのか。pdfjs-dist はレンダリング指向のライブラリで、テキストや画像の「表示に必要な情報」を効率的に取得できます。一方、カタログ辞書のエントリ一覧やオブジェクトの統計情報など、PDFの「ファイル構造そのもの」への低レベルアクセスは pdf-lib の方が適しています。

両者はそれぞれ独立してPDFをロードし、得意な領域の情報を返します。依存関係はありません。

### stdout ガード — pdfjs-dist の罠

:::message alert
MCPサーバーは stdio（標準入出力）を使ってJSON-RPCで通信します。ところが pdfjs-dist の内部では、警告メッセージを `console.log`（= stdout）に出力するコードがあります。
:::

これが致命的です。MCPクライアントが受け取る JSON-RPC ストリームに、pdfjs-dist の警告テキストが混入し、パースエラーになります。
```typescript
// src/index.ts — MCPサーバーのエントリーポイント

// IMPORTANT: Guard stdout before any imports.
// pdfjs-dist's warn() uses console.log (= stdout), which corrupts the
// stdio JSON-RPC stream. Redirect console.log/console.warn to stderr.
const _originalConsoleLog = console.log;
const _originalConsoleWarn = console.warn;
console.log = (...args: unknown[]) => console.error('[log]', ...args);
console.warn = (...args: unknown[]) => console.error('[warn]', ...args);
```

**インポートより前に** `console.log` を `console.error`（= stderr）にリダイレクトします。これで pdfjs-dist の内部警告は stderr に流れ、JSON-RPC ストリームは汚染されません。

加えて、pdfjs-dist のロード時に `verbosity: 0`（ERRORS のみ）を指定し、そもそも不要な警告を抑制しています。
```typescript
const PDFJS_VERBOSITY = 0; // VerbosityLevel.ERRORS

export async function loadDocument(filePath: string): Promise<PDFDocumentProxy> {
  const data = await readPdfFile(filePath);
  const doc = await getDocument({
    data,
    useSystemFonts: true,
    verbosity: PDFJS_VERBOSITY
  }).promise;
  return doc;
}
```

この問題は pdf-spec-mcp の開発時にも遭遇していたので、対処法は分かっていました。pdfjs-dist を使う MCP サーバーを作る人は、ほぼ確実にこの罠にはまるはずです。

### 並列ページ処理による高速化

v0.2.0 で、ページ処理を `Promise.all` による並列化に変更しました。pdfjs-dist は内部的にページごとの独立性が保たれており、複数ページの並列アクセスが安全に行えます。
```typescript
// Before: 逐次処理
for (const pageNum of pageNumbers) {
  const page = await doc.getPage(pageNum);
  const text = await extractPageText(page);
  results.push({ page: pageNum, text });
}

// After: 並列処理
const results = await Promise.all(
  pageNumbers.map(async (pageNum) => {
    const page = await doc.getPage(pageNum);
    const text = await extractPageText(page);
    return { page: pageNum, text };
  }),
);
```

この変更だけで、主要なツールのパフォーマンスが大幅に改善しました。

| ツール | 改善幅 |
| --- | --- |
| `searchText` | **~68%** 高速化 |
| `analyzeFonts` | **~57%** 高速化 |
| `getMetadata` | **~27%** 高速化 |
| `validateMetadata` | **~25%** 高速化 |

`validateTagged` では、ドキュメントの二重ロードを排除し、タグ解析と画像カウントを `Promise.all` で並列実行するようにしました。
```typescript
// Before: ドキュメントを2回ロード
const tags = await analyzeTags(filePath);      // loadDocument() 1回目
const images = await countImages(filePath);    // loadDocument() 2回目

// After: 1回のロードで並列実行
const doc = await loadDocument(filePath);
const [tags, imageCount] = await Promise.all([
  analyzeTagsFromDoc(doc),
  countImagesFromDoc(doc),
]);
await doc.destroy();
```

### テストフィクスチャの自動生成

テスト用PDFは pdf-lib を使ってコードで生成しています。
```typescript
// tests/fixtures/create-test-pdf.ts
async function createSimplePdf(): Promise<void> {
  const doc = await PDFDocument.create();
  const font = await doc.embedFont(StandardFonts.Helvetica);

  const page1 = doc.addPage([595, 842]); // A4
  page1.drawText('Hello PDF World', {
    x: 50, y: 780, size: 24, font
  });
  // ...

  doc.setTitle('Test PDF Document');
  doc.setAuthor('pdf-reader-mcp');

  const bytes = await doc.save();
  await writeFile(`${FIXTURES_DIR}/simple.pdf`, bytes);
}
```

手作業でPDFを作成する方式と比べて、コード生成には以下の利点があります。

- **再現性** — `npm run test:fixtures` で常に同じPDFが生成される
- **バリエーション** — 注釈付き、署名フィールド付き、多フォントなど、テスト条件に特化したPDFを簡単に作れる
- **CI対応** — GitHub Actions で自動テストが回せる

E2Eテストは9スイート・146テストケースを実施しており、v0.2.0 時点で全テスト通過しています。

## pdf-spec-mcp との連携

pdf-reader-mcp は**単体で全15ツールが動作します**。pdf-spec-mcp への依存はありません。

ただし、両方を有効にすると、LLMは「仕様知識に基づいた構造解析」というワークフローを実行できます。
```
┌──────────────────┐              ┌──────────────────┐
│ pdf-reader-mcp   │              │  pdf-spec-mcp    │
│ 「実物を読む」     │              │ 「仕様を引く」      │
│                  │              │                  │
│ summarize        │─── ① ──▶    │                  │
│ inspect_tags     │─── ② ──▶    │                  │
│                  │              │ get_requirements │─── ③
│ validate_tagged  │─── ④ ──▶    │                  │
│ compare_structure│─── ⑤ ──▶    │                  │
└──────────────────┘              └──────────────────┘
```

1. `summarize` でPDFの概要を把握
2. `inspect_tags` でタグ構造を確認
3. pdf-spec-mcp の `get_requirements` で PDF/UA 要件を取得
4. `validate_tagged` で適合性を検証
5. `compare_structure` で修正前後の構造差分を確認

「仕様を引く」ツールと「実物を読む」ツール。この2つが揃って初めて、LLMは「このPDFは仕様に準拠しているか？」に答えられるようになります。

これは前回の記事で紹介した DeepL MCP との連携と同じ発想です — 独立したMCPサーバー同士を組み合わせることで、単体ではできないワークフローが生まれます。

## セットアップ

### npx で即実行（インストール不要）

Claude Desktop の `claude_desktop_config.json` に追加するだけです。
```json
{
  "mcpServers": {
    "pdf-reader": {
      "command": "npx",
      "args": ["-y", "@shuji-bonji/pdf-reader-mcp"]
    }
  }
}
```

### Claude Code
```bash
claude mcp add pdf-reader-mcp -- npx -y @shuji-bonji/pdf-reader-mcp
```

### pdf-spec-mcp との併用
```json
{
  "mcpServers": {
    "pdf-reader": {
      "command": "npx",
      "args": ["-y", "@shuji-bonji/pdf-reader-mcp"]
    },
    "pdf-spec": {
      "command": "npx",
      "args": ["-y", "@shuji-bonji/pdf-spec-mcp"],
      "env": {
        "PDF_SPEC_DIR": "/path/to/pdf-specs"
      }
    }
  }
}
```

## まとめ

pdf-reader-mcp は「PDFの内部構造をLLMが読み解けるようにする」MCPサーバーです。

- **テキスト抽出の先へ** — カタログ辞書、タグツリー、フォント、電子署名など、PDFの内部構造に踏み込む15ツール
- **3 Tier アーキテクチャ** — 基本操作 → 構造解析 → 検証・分析と段階的に深く潜れる設計
- **pdfjs-dist + pdf-lib** — レンダリング指向と構造指向、2つのライブラリの得意領域を使い分け
- **単体で完結、組み合わせで拡張** — pdf-spec-mcp と併用すれば、仕様知識に基づいた検証ワークフローが可能に

このプロジェクトは、筆者が電子署名ソフトの開発で日常的に行っていた「PDFの中身を覗く」作業を、LLMでも再現できるようにしたいという動機から生まれました。既存のPDF MCPサーバーがテキスト抽出の薄いラッパーに留まっていた現状に対する、一つの回答です。
