## はじめに

ブラウザ上のアプリに AI エージェントを介入させたい。そう考えたとき、選択肢は一つではありません。

2025年から2026年にかけて、ブラウザと AI エージェントを繋ぐ仕組みが急速に整備されてきました。Microsoft の **Playwright MCP**、W3C で標準化が進む **WebMCP**、そしてその polyfill でもある **MCP-B**。いずれも「AI がブラウザ上のアプリを操作する」ことを可能にしますが、アプローチが根本的に異なります。

この記事では、個人開発している会計 PWA「**e-shiwake**」に WebMCP を実装した経験を踏まえて、3つの仕組みを**アプリ開発者の視点**で比較します。特に、**サーバーを持たないローカルファースト PWA** にとって、どの選択肢が現実的かという観点に重点を置きます。

### 対象読者

- AI エージェントとの統合に関心がある Web 開発者
- PWA やローカルファーストなアプリを作っている方
- Playwright MCP を使っているが「もっと確実な方法はないか」と思っている方

### 関連記事

WebMCP の実装詳細は別記事にまとめています。本記事は「なぜ WebMCP を選んだのか」という比較・選定の話です。

https://zenn.dev/shuji_bonji/articles/29b8d3ee2d89a9

## 3つのアプローチ：外から操作 vs 中からツール公開

ブラウザ上のアプリに AI を介入させる方法は、大きく2つの方向に分かれます。


### 「外から操作」
- AI がブラウザを自動操縦してボタンを押す、テキストを入力する。
- アプリ側の変更は不要
- 例）Playwright MCP  

### 「中からツール公開」
- アプリが自分の機能を「ツール」として AI に教える。
- AI はツールを呼び出すだけで、UI 操作はしない。
- 例）WebMCP / MCP-B  


この違いは「AI がアプリの構造を理解しているかどうか」に直結します。

## Playwright MCP：外からブラウザを操る

### 概要

[Playwright MCP](https://github.com/microsoft/playwright-mcp) は Microsoft が開発した MCP サーバーです。Playwright（ブラウザ自動化ライブラリ）を通じて、LLM がブラウザを操作できるようにします。

```
LLM → MCP Client → Playwright MCP Server → ブラウザ自動操作
                                              ↓
                                        アクセシビリティツリーを解析
                                        ボタンをクリック、テキストを入力
```

### 特徴

**強み：アプリ側の変更が一切不要**

どんな Web アプリでも、そのまま操作できます。アプリ開発者が何もしなくても、AI がアクセシビリティツリーを読み取り、画面を理解して操作します。

```typescript
// MCP クライアント側の設定だけで動く
{
  "command": "npx",
  "args": ["@playwright/mcp@latest"]
}
```

**弱み：「推測」で操作するしかない**

Playwright MCP は画面の構造（アクセシビリティツリー）を見て「たぶんこのボタンが検索だろう」と推測して操作します。

AI の思考プロセス
```
  「このページに入力欄が3つとボタンが1つある」
  「ラベルに"検索"と書いてある...たぶんこれが検索ボタン？」
  → クリック → 画面遷移を待つ → 結果をパース
```

この「推測」には限界があります。

- **Shadow DOM** の中にある要素は見えないことがある
- UI が変更されると動かなくなる（CSS クラス名の変更だけで壊れることも）
- 操作ごとに数秒〜十数秒かかる（人間の操作速度を模倣するため）
- 認証が必要なページでは、毎回ログインフローが必要

### どんなケースに向いているか

- **E2E テスト**：アプリの動作を網羅的にテストする
- **対応していないサイトの操作**：自分が開発していない外部サービスを自動化する
- **スクレイピング的な用途**：サイトからデータを取得する

## WebMCP：中からツールを公開する（W3C 標準）

### 概要

[WebMCP](https://webmachinelearning.github.io/webmcp/) は W3C で標準化が進んでいるブラウザ API です。Web アプリが `navigator.modelContext` を通じて、自分の機能を「ツール」として AI エージェントに公開します。

```
Web アプリ → navigator.modelContext.registerTool() → ブラウザ
                                                        ↓
                                              AI エージェント（拡張機能等）
                                                        ↓
                                              ツールを呼び出し → 結果を受け取る
```

### 特徴

**強み：開発者が「正しい使い方」を定義する**

AI は推測する必要がありません。開発者が「このツールはこういう引数を受け取り、こういう結果を返す」と明確に定義します。

```typescript
navigator.modelContext.registerTool({
  name: 'search_journals',
  description: '仕訳を検索する。キーワード、科目名、金額、日付で検索可能。',
  inputSchema: {
    type: 'object',
    properties: {
      query: { type: 'string', description: '検索クエリ' }
    },
    required: ['query']
  },
  execute: async (input) => {
    // IndexedDB を直接検索 → 構造化 JSON を返す
    const results = await searchJournals(input.query);
    return { content: [{ type: 'text', text: JSON.stringify(results) }] };
  }
});
```

REST API のエンドポイント定義と同じ感覚です。

**強み：ミリ秒単位で結果が返る**

ブラウザ内で関数を直接呼び出すため、ネットワーク通信はゼロ。Playwright MCP が1回の操作に数秒かかるのに対して、WebMCP はミリ秒で完了します。

**強み：UI と同期できる**

ツール実行後に `CustomEvent` を発火することで、画面をリアルタイムに更新できます。Playwright MCP では「操作結果を確認するために画面を再読み込み」が必要ですが、WebMCP なら操作と UI 更新がシームレスに連動します。

**弱み：アプリ側の実装が必要**

開発者がツールを定義しなければ何も起きません。対応していないアプリには使えません。

**弱み：Chrome 146+ 限定（2026年2月時点）**

`chrome://flags` → **WebMCP for testing** を有効にする必要があり、一般ユーザーにはまだ届いていません。

### どんなケースに向いているか

- **自分が開発しているアプリ**：機能を確実に公開したい場合
- **ローカルファーストアプリ**：サーバーがなくても AI 連携を実現したい場合
- **将来のブラウザ標準**に乗りたい場合

## MCP-B：WebMCP の polyfill + MCP ブリッジ

### 概要

[MCP-B](https://mcp-b.ai/)（Model Context Protocol for Browser）は、Amazon エンジニアの Alex Nahas が開発したプロジェクトです。GitHub リポジトリ名は [WebMCP](https://github.com/MiguelsPizza/WebMCP) で、実質的に **WebMCP の先行実装かつリファレンス実装** です。

```
Web アプリ → TabServerTransport → MCP-B 拡張機能 → Native Messaging → Claude Desktop
                (postMessage)       (Chrome 拡張)      (ブラウザ外部)     (MCP Client)
```

### WebMCP との関係

MCP-B と WebMCP は「別物」ではなく、**同じビジョンの異なるレイヤー**です。

```
WebMCP（W3C 標準仕様）
  ├── Chrome 146 ネイティブ実装（navigator.modelContext）← 実験的
  └── MCP-B
       ├── @mcp-b/webmcp-polyfill  ← 未対応ブラウザに navigator.modelContext を提供
       └── @mcp-b/global           ← polyfill + MCP 外部接続ブリッジ
```

MCP-B は W3C の WebMCP 標準化プロセスにも参加しています。Chrome、Edge、MCP-B の開発者が共同で仕様を策定しているという状況です。

なお、MCP-B の Chrome 拡張はクローズドソースに移行し、トランスポート等のオープンソース部分は [WebMCP-org](https://github.com/WebMCP-org) に引き継がれています。

### 特徴

**強み：外部 MCP クライアントと接続できる**

WebMCP（`navigator.modelContext`）は現状 Inspector 拡張でしか使えません。MCP-B は Chrome 拡張 + Native Messaging を通じて、**Claude Desktop や Cursor から直接ブラウザ内のツールを呼び出せます**。

```
WebMCP のみ：
  Inspector → ブラウザ内ツール（ブラウザ内完結）

MCP-B：
  Claude Desktop → Native Messaging → MCP-B 拡張 → ブラウザ内ツール
  （ブラウザ外部から呼べる）
```

**強み：認証の問題を解決する**

MCP-B が生まれた背景は、Amazon 内部での認証問題でした。OAuth 2.1 の実装は現実的に困難で、ブラウザの既存セッション（SSO、Cookie）をそのまま使いたかった。MCP-B はブラウザ内で動作するため、ユーザーが既にログインしている状態をそのまま AI エージェントが利用できます。

**弱み：Chrome 拡張への依存**

MCP-B は Chrome 拡張として動作するため、Safari や Firefox では使えません（Firefox 対応は計画中）。

### どんなケースに向いているか

- **今すぐ Claude Desktop 等から Web アプリを操作したい**場合
- 認証済みセッションを AI に共有したい場合
- WebMCP が正式対応するまでの polyfill として

## 比較表

| 観点 | Playwright MCP | WebMCP | MCP-B |
|------|---------------|--------|-------|
| **方向** | 外→中（操作） | 中→外（公開） | 中→外（公開） |
| **アプリ側の変更** | 不要 | 必要 | 必要 |
| **AI の理解度** | 推測（DOM/a11y） | 正確（開発者定義） | 正確（開発者定義） |
| **速度** | 数秒〜十数秒/操作 | ミリ秒 | ミリ秒 |
| **UI との同期** | 画面リロードが必要 | CustomEvent で即時 | CustomEvent で即時 |
| **認証** | 新規セッション | 同一ページ内（不要） | ブラウザセッション継承 |
| **接続先** | Claude Desktop, Cursor 等 | Inspector 拡張のみ | Claude Desktop, Cursor 等 |
| **ブラウザ対応** | Chromium, Firefox, WebKit | Chrome 146+ のみ | Chromium 系 |
| **成熟度** | 本番利用可 | 実験段階 | 利用可 |
| **標準化** | なし（Microsoft 独自） | W3C 提案中 | W3C に参加 |
| **開発元** | Microsoft | Google + Microsoft（W3C） | Alex Nahas（Amazon） |

## サーバーの有無で変わる選択肢

ここからがこの記事の本題です。

3つの仕組みを比較した上で、**アプリのアーキテクチャによって最適解が変わる**ことに気づきました。

### Web サービス（サーバーあり）の場合

freee、Slack、GitHub... のような Web サービス 

:::message
**すでに REST API がある**
- Web API MCP Server を作れば AI 連携は完了
- WebMCP 対応は「あれば便利」程度
- 何もしなくても Playwright MCP で操作される
:::

既存の REST API のエンドポイントを MCP のツール定義に変換するだけで済みます。WebMCP は追加の選択肢として「認証不要で軽量」というメリットがありますが、必須ではありません。

### ローカルファースト PWA（サーバーなし）の場合

:::message
**e-shiwake のようなローカルファースト PWA**
- **WebAPIサーバーがない**
   - Web API MCP Server は作れない
   - Playwright MCP は使えるが推測ベースで壊れやすい
   - WebMCP / MCP-B が唯一の確実な手段

選択肢: WebMCP 一択（+ MCP-B で外部接続）
:::

これがまさに e-shiwake で直面した状況です。

### 比較：同じ「仕訳検索」を3つの方法で

具体的に、e-shiwake の仕訳検索を3つのアプローチで実現する場合を比べてみましょう。

**Playwright MCP の場合**

:::message
AI → Playwright → e-shiwake のページを開く
  → 検索ボックスを見つける（a11y ツリー解析）
  → "消耗品費" と入力
  → 検索結果が表示されるのを待つ
  → テーブルの内容をパース
  → 結果を構造化して返す

所要時間: 5〜15秒
信頼性: UI 変更で壊れるリスクあり
:::

**WebMCP の場合**

:::message
AI → navigator.modelContext → search_journals({ query: "消耗品費" })
  → IndexedDB を直接クエリ
  → 構造化 JSON を返す

所要時間: 数ミリ秒
信頼性: 開発者が定義しているので確実
:::

**Web API MCP の場合**
:::message
（サーバーがないので不可能）
:::

この差は、1回のツール呼び出しで見れば「速度の違い」ですが、AI エージェントが複数のツールを組み合わせて作業する場合は**決定的な差**になります。

## WebMCP は「ブラウザ内の MCP サーバー」

実装してみて気づいたのは、WebMCP のツール定義は REST API のエンドポイント定義と**ほぼ同じ構造**だということです。

```
REST API:
  POST /api/journals/search
  Body: { "query": "消耗品費" }
  Response: { "count": 5, "journals": [...] }

WebMCP:
  Tool: search_journals
  Input: { "query": "消耗品費" }
  Output: { "count": 5, "journals": [...] }
```

どちらも「名前 + 入力スキーマ + 実行 → 構造化データ」というパターンです。違いは実行場所だけ。

| 観点 | Web API MCP | WebMCP |
|------|-------------|--------|
| 実行場所 | サーバー | ブラウザ内 |
| ネットワーク | HTTP（認証必要） | 不要（同一プロセス） |
| データアクセス | API が公開している範囲 | アプリ内部に直接アクセス可能 |
| UI 連携 | 不可（API は UI を知らない） | CustomEvent で即時反映 |

つまり、**サーバーのある Web サービスにとっては「REST API の別表現」、サーバーのない PWA にとっては「唯一の API 公開手段」**です。

## 各プラットフォームのAI介入の現状

ここまでブラウザの話をしてきましたが、「AI がアプリに介入する仕組み」はブラウザだけの話ではありません。各プラットフォームで同様の動きが進んでいます。


### AI がアプリに介入する仕組みづくり（2026年2月時点）

|プラットフォーム | 外から操作 |中からツール公開 | 進行度|
| --- |--- |--- |--- |
| サーバー | SSH + CLI | MCP Server（REST API） | ✅ 成熟 |
| クラウド DB | — | DB MCP Server（Google等） | ✅ 成熟 |
| ブラウザ | Playwright MCP | WebMCP / MCP-B | 🧪 実験 |
| Windows | Computer Use（CUA） | Windows MCP ネイティブ | 🔜 準備中|
| iOS / macOS | mobile-mcp | App Intents + MCP | 🔜 計画中|
| Android | mobile-mcp | （未定） | ❓ |

注目すべきは、**すべてのプラットフォームで「外から操作」と「中からツール公開」の両方が進行している**こと。そしてどのプラットフォームでも、「中からツール公開」の方が精度・速度・信頼性で優れています。

### Apple の App Intents

> Apple は **App Intents** フレームワークを通じて、ネイティブアプリが Siri / Apple Intelligence にツールを公開する仕組みをすでに持っています。iOS 26.1 beta では MCP との統合コードも発見されており、App Intents + MCP の組み合わせが実現すれば、ChatGPT や Claude といったサードパーティ AI からも iPhone / Mac アプリを操作できるようになります。

App Intents に対応していないアプリは「AI にとって見えない存在」になると言われており、**WebMCP でツールを公開しないWebアプリ**にも同じことが言えるでしょう。

### Microsoft の Windows MCP

> Microsoft は Windows 11 で MCP をネイティブサポートする計画を発表しています。File Explorer や Windows Settings には組み込みの MCP コネクタが用意され、Copilot Studio からデスクトップアプリを操作できるようになります。API がないアプリ向けには **Computer Use Agent（CUA）** という Playwright MCP のデスクトップ版も提供されます。

### PWA の独自のポジション

ここで面白いのが **PWA の立ち位置** です。

```
ネイティブアプリ:
  iOS    → App Intents で AI 連携 ✅（ただし iOS 限定）
  Android → まだ手段がない ❓
  Windows → Windows MCP で AI 連携 🔜（ただし Windows 限定）

PWA:
  どの OS でも → ブラウザが WebMCP をサポートすれば AI 連携可能
  = クロスプラットフォームで AI 連携できる唯一のアプリ形態（将来的に）
```

ネイティブアプリは OS ごとに異なる仕組み（App Intents、Windows MCP、...）に対応する必要があります。一方 PWA は、WebMCP が W3C 標準として全ブラウザに実装されれば、**一度の実装でどの OS でも AI 連携が可能** になります。

## まだ「土台を作っている」段階

ここまで見てきた通り、AI がアプリに介入するための仕組みは**まさに今、各プラットフォームで構築されている最中**です。

| 環境 | ステータス | 進捗 |
--- | --- | ---
サーバー側     | MCP Server 標準化済み               |    ✅
ブラウザ       | WebMCP 実験中、MCP-B 利用可          |   🧪
iOS / macOS   | App Intents + MCP コード発見        |     🔜
Windows       | Windows MCP ネイティブ計画           |    🔜
Android       | 外から操作のみ                        |   ❓
クロスプラット | W3C エージェント通信標準 2026-2027 予定  | ❓

すべてが揃うのはまだ先です。でも、サーバー側の MCP が2024年末に登場してからわずか1年半で、ブラウザ、デスクトップ、モバイルにまで広がっています。

**今は「AI がアプリを使う」ためのインフラを作っている段階** であり、このインフラを作れるのは AI ではなく、アーキテクチャを設計できるエンジニアです。

## まとめ

### どの仕組みを選ぶべきか

```
「自分が開発していないサイトを AI で操作したい」
  → Playwright MCP

「自分のアプリの機能を AI に公開したい」
  → WebMCP（将来の標準）/ MCP-B（今すぐ使える）

「サーバーのない PWA に AI 連携を組み込みたい」
  → WebMCP が唯一の確実な手段
```

### PWA 開発者へ

サーバーがなくても、AI エージェント連携はできます。

WebMCP は「ブラウザ内に埋め込まれた MCP サーバー」です。REST API を書くのと同じ感覚でツールを定義すれば、AI がアプリのデータを理解して操作できるようになります。

実装は既存のロジックを再利用するだけで、アプリの通常動作には一切影響しません（フィーチャーフラグで分離可能）。まだ実験段階ですが、今のうちに触れておく価値はあると思います。
