## はじめに

RFC を読んでいて、こんな経験はありませんか？

- 英語のまま読むのは辛い
- 機械翻訳すると技術用語がおかしくなる
- 「MUST」「SHOULD」「MAY」の要件だけでも正確に把握したい

今回、**複数の MCP サーバーを連携** させて、RFC の翻訳ワークフローを構築してみました。

この記事は「MCP 連携の実践例」として記録に残すものです。

## 🎯 やりたかったこと

RFC 6455（WebSocket Protocol）を日本語で読みたい。

ただし、単純な機械翻訳ではなく：

1. **要件（MUST/SHOULD/MAY）を構造的に抽出**したい
2. **翻訳品質を数値で確認**したい
3. **AI と対話しながら進めたい**

## 🧩 使用した MCP サーバー

3つの自作 MCP サーバーを連携させました。

```
┌─────────────────┐
│  rfcxml-mcp     │  RFC から要件を構造化抽出
│  （MUST/SHOULD） │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  deepl-mcp      │  日本語に翻訳
│  （DeepL API）   │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  xcomet-mcp     │  翻訳品質をスコアリング
│  （0〜1 評価）   │
└─────────────────┘
```

| MCP サーバー | 役割 | npm |
|-------------|------|-----|
| rfcxml-mcp | RFC 構造解析・要件抽出 | [@shuji-bonji/rfcxml-mcp](https://www.npmjs.com/package/@shuji-bonji/rfcxml-mcp) |
| deepl-mcp | DeepL 翻訳 | [deepl-mcp-server](https://github.com/DeepLcom/deepl-mcp-server) |
| xcomet-mcp | 翻訳品質評価 | [@shuji-bonji/xcomet-mcp](https://www.npmjs.com/package/xcomet-mcp-server) |

## 🔧 セットアップ

MCP 対応環境であれば利用可能です。

- Claude Desktop
- Claude Code
- Cursor
- その他 MCP クライアント

```json
{

    }
  }
}
```

## 🚀 実践：RFC 6455 翻訳ワークフロー

### Step 1: 要件抽出

#### Claude への依頼

```
RFC 6455 の実装チェックリストを生成してください。
```

rfcxml-mcp が RFC 6455 を解析し、要件を構造化して返します。

#### 結果

| 要件レベル | 件数 |
|-----------|------|
| MUST / REQUIRED / SHALL | 124 |
| SHOULD / RECOMMENDED | 31 |
| MAY / OPTIONAL | 46 |

セクション別に整理されたチェックリストが生成されました。

```markdown
## 5. Data Framing

### 5.1. Overview
- [ ] A client MUST mask all frames that it sends to the server.
- [ ] The server MUST close the connection upon receiving a frame that is not masked.

### 5.2. Base Framing Protocol  
- [ ] The FIN bit MUST be set to 1 for the final fragment.
...
```

### Step 2: 翻訳

#### Claude への依頼

```
このチェックリストを日本語に翻訳してください。
```

deepl-mcp が DeepL API を呼び出し、翻訳を実行。

#### 翻訳例

| 原文 | 翻訳 |
|------|------|
| A client MUST mask all frames that it sends to the server. | クライアントは、サーバーに送信するすべてのフレームをマスクしなければならない（MUST）。 |
| The server MUST close the connection upon receiving a frame that is not masked. | サーバーは、マスクされていないフレームを受信した場合、接続を閉じなければならない（MUST）。 |

技術用語（frame, mask, connection）は適切に処理され、RFC 2119 キーワード（MUST）も保持されています。

### Step 3: 品質評価

#### Claude への依頼

```
翻訳品質を評価してください。
```

xcomet-mcp が xCOMET モデルで翻訳品質をスコアリング。

#### 評価結果例

```json
{
  "score": 0.89,
  "quality": "Good",
  "errors": []
}
```

| スコア | 品質判定 | 意味 |
|--------|---------|------|
| 0.9〜1.0 | Excellent | そのまま使える |
| 0.7〜0.9 | Good | 軽微なレビュー推奨 |
| 0.5〜0.7 | Acceptable | 要編集 |
| 0.0〜0.5 | Poor | 再翻訳推奨 |

### Step 4: 問題箇所の特定と改善

スコアが低い箇所がある場合：

```
スコアが 0.7 未満の翻訳を特定し、改善案を出してください。
```

xcomet-mcp がエラー箇所を重要度別（minor / major / critical）に検出し、Claude が改善案を提示。

## 📊 結果まとめ

RFC 6455 全体の翻訳ワークフローを実行した結果：

| 指標 | 値 |
|------|-----|
| 抽出した要件数 | 201件（MUST 124 + SHOULD 31 + MAY 46） |
| 翻訳対象 | 約 15,000 語 |
| 平均品質スコア | 0.85〜0.90（Good） |
| 作業時間 | 数時間（手動なら数日） |

## 💡 MCP 連携で気づいたこと

### 良かった点

1. **各ツールが得意なことに集中**
   - rfcxml-mcp: RFC の構造解析に特化
   - deepl-mcp: 翻訳に特化
   - xcomet-mcp: 品質評価に特化

2. **Claude が「接着剤」になる**
   - 各 MCP の出力を次の MCP に渡す
   - 人間は「次に何をするか」を指示するだけ

3. **中間結果を確認しながら進められる**
   - 要件抽出の結果を見てから翻訳
   - 翻訳結果を見てから品質評価
   - 問題があれば戻って修正

### 課題

1. **古い RFC は精度が下がる**
   - RFC 8650 以前は RFCXML がないためテキスト解析にフォールバック
   - 正規表現ベースの抽出は完璧ではない

2. **xCOMET はローカル実行が重い**
   - GPU がないと評価に時間がかかる
   - 大量評価にはサーバー化が必要

3. **MCP 設定の手間**
   - 複数 MCP を設定するのは初回だけ面倒
   - 一度設定すれば再利用できる

## おわりに

複数の MCP サーバーを組み合わせることで、「RFC を読む」という作業が「AI と一緒に RFC を理解する」体験に変わりました。

MCP の真価は**連携**にあると感じています。

単体でも便利ですが、組み合わせることで単体では実現できないワークフローが構築できる。これが MCP エコシステムの面白さだと思います。

RFC に限らず、「複数の処理を繋げたい」場面があれば、MCP 連携を検討してみてください。
