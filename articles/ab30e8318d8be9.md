## はじめに

PDF関連のソフトウェアを開発していると、ISO 32000（PDF仕様書）を頻繁に参照します。筆者は電子署名ソフトの開発に携わっており、デジタル署名（12.8節）や暗号化（7.6節）のセクションは日常的に確認する必要があります。

しかし、この仕様書には2つの大きな壁があります。

**1. PDF 2.0 の情報がネット上に少ない**

PDF 1.7（ISO 32000-1）は Adobe が無料公開していたため、ブログ記事やStack Overflowに情報が豊富です。一方、PDF 2.0（ISO 32000-2:2020）はISO規格として策定されたため、ネット上の解説は英語でもまだ少なく、日本語ではほぼゼロです。

電子署名周りは 2.0 で大きく変わっています。PAdES対応、AES-GCMによる暗号化、新しい署名フィールド構造など — これらの情報は仕様書を直接読むしかありません。

**2. 1,020ページの仕様書をLLMが参照できない**

Claude や GPT に「PDF 2.0 のデジタル署名の仕様を教えて」と聞いても、学習データに含まれる断片的な情報しか返ってきません。PDF をアップロードすることもできますが、1,020ページの仕様書全体を毎回渡すのは非現実的です。

そこで作ったのが **pdf-spec-mcp** です。

https://github.com/shuji-bonji/pdf-spec-mcp

## pdf-spec-mcp とは

MCP（Model Context Protocol）サーバーとして、LLM に PDF仕様書への構造的なアクセスを提供するツールです。「PDFファイルを読む」のではなく、「PDF仕様書を"引く"」ことに特化しています。

```
┌─────────────────────────────────────┐
│         AI Agent（Claude等）          │
│  「12.8節のデジタル署名の要件は？」    │
└──────────────┬──────────────────────┘
               │ MCP Tool Call
               ▼
┌─────────────────────────────────────┐
│          pdf-spec-mcp               │
│  get_section({ section: "12.8" })   │
│  get_requirements({ section: "12.8",│
│                     level: "shall"})│
└──────────────┬──────────────────────┘
               │ 構造化データ
               ▼
┌─────────────────────────────────────┐
│      ISO 32000-2 PDF (1,020頁)       │
│      985セクション・71定義語          │
└─────────────────────────────────────┘
```

### 既存のPDF系MCPサーバーとの違い

「PDF」と名前の付くMCPサーバーは既にいくつか存在しますが、それらは**汎用的なPDFファイルリーダー**です。任意のPDFからテキストや画像を抽出するのが目的です。

pdf-spec-mcp はアプローチが異なります。

| 比較項目 | 汎用 PDF リーダー系 MCP | pdf-spec-mcp |
|---|---|---|
| 対象 | 任意のPDFファイル | PDF**仕様書**（ISO 32000 ファミリー） |
| 出力 | 生テキスト・画像 | **構造化データ**（見出し・段落・テーブル・注記） |
| 操作 | 「このPDFを読んで」 | 「7.3.4節を見せて」「digital signatureを検索」 |
| セクション認識 | なし | 985セクションのインデックス |
| 要件抽出 | なし | shall / must / may の正規要件を抽出 |

仕様書の構造を理解した上で情報を返すので、LLM が仕様に基づいた正確な回答を生成できます。

## 8つのツール

pdf-spec-mcp は8つのツールを提供します。実際の実行例と合わせて紹介します。

### 1. `list_specs` — 利用可能な仕様書一覧

環境変数 `PDF_SPEC_DIR` で指定したディレクトリ内のPDF仕様書を自動検出します。ファイル名パターンで最大17種類のドキュメントを識別します。

```json
// list_specs の結果（抜粋）
[
  { "id": "iso32000-2", "title": "ISO 32000-2:2020 (PDF 2.0)", "pages": 1020, "sections": 985 },
  { "id": "pdf17",      "title": "ISO 32000-1 (PDF 1.7)",      "pages": 756,  "sections": 652 },
  { "id": "pdfua2",     "title": "PDF/UA-2 (ISO 14289-2)",     "pages": 42,   "sections": 87  },
  { "id": "ts32002",    "title": "TS 32002 (Digital Signatures)", "pages": 28 }
]
```

対応ドキュメント：

| カテゴリ | ドキュメント |
|---|---|
| 標準規格 | ISO 32000-2（PDF 2.0）、ISO 32000-1（PDF 1.7） |
| 技術仕様 | TS 32001〜32005（ハッシュ、デジタル署名、AES-GCM等） |
| アクセシビリティ | PDF/UA-1、PDF/UA-2 |
| ガイド | Tagged PDF Best Practice Guide、Well-Tagged PDF |

### 2. `get_structure` — セクション階層（目次）

```json
// get_structure({ max_depth: 2 })
{
  "title": "ISO 32000-2:2020 (PDF 2.0)",
  "totalSections": 985,
  "sections": [
    {
      "sectionNumber": "7",
      "title": "Syntax",
      "children": [
        { "sectionNumber": "7.1", "title": "General" },
        { "sectionNumber": "7.2", "title": "Lexical conventions" },
        { "sectionNumber": "7.3", "title": "Objects" },
        { "sectionNumber": "7.4", "title": "Filters" }
      ]
    },
    {
      "sectionNumber": "12",
      "title": "Interactive features",
      "children": [
        { "sectionNumber": "12.7", "title": "Forms" },
        { "sectionNumber": "12.8", "title": "Digital signatures" }
      ]
    }
  ]
}
```

`max_depth` でツリーの深さを制御できます。1020ページの仕様書でも、LLMが必要な粒度でナビゲーションできます。

### 3. `get_section` — セクション内容の取得

これが中核のツールです。セクション番号を指定すると、構造化されたコンテンツを返します。

```json
// get_section({ section: "7.3.4" })
{
  "section": "7.3.4",
  "title": "String objects",
  "pages": { "start": 62, "end": 66 },
  "content": [
    { "type": "heading", "level": 3, "text": "7.3.4 String objects" },
    { "type": "heading", "level": 4, "text": "7.3.4.1 General" },
    { "type": "paragraph", "text": "A string object shall consist of..." },
    { "type": "note", "label": "NOTE 1", "text": "This standard does not..." },
    { "type": "table", "headers": ["Sequence", "Meaning"], "rows": [
      ["\\n", "LINE FEED (0Ah)"],
      ["\\r", "CARRIAGE RETURN (0Dh)"]
    ]},
    { "type": "list", "items": ["Hexadecimal data...", "ASCII base-85..."] }
  ]
}
```

生テキストではなく、見出し・段落・テーブル・リスト・注記が型付きで返ります。LLMはこの構造を理解して、的確な回答を組み立てられます。

### 4. `search_spec` — 全文検索

```json
// search_spec({ query: "digital signature", max_results: 5 })
{
  "query": "digital signature",
  "totalResults": 5,
  "results": [
    { "section": "12.8.1", "title": "General", "page": 592, "score": 8,
      "snippet": "...a digital signature may be used to authenticate..." },
    { "section": "12.8.2", "title": "Transform methods", "page": 595, "score": 6,
      "snippet": "...the digital signature handler..." }
  ]
}
```

初回検索時にインデックスを構築（約4秒）、以降はキャッシュで即時応答します。

### 5. `get_requirements` — 正規要件の抽出

ISO規格では shall / must / may が厳密に定義されています。このツールはセクション内の要件文を抽出・分類します。

```json
// get_requirements({ section: "12.8", level: "shall" })
{
  "section": "12.8",
  "requirements": [
    {
      "level": "shall",
      "text": "The signature handler shall compute...",
      "context": "12.8.1 General"
    }
  ]
}
```

「この機能を実装するとき、仕様上 MUST な要件は何か？」という質問に直接答えられます。

### 6. `get_definitions` — 用語定義の参照

ISO 32000-2 の第3節で定義されている71個の専門用語を検索・取得します。

```json
// get_definitions({ term: "signature" })
{
  "definitions": [
    {
      "term": "digital signature",
      "definition": "data appended to, or a cryptographic transformation of..."
    }
  ]
}
```

### 7. `get_tables` — テーブル構造の抽出

PDF仕様書にはキーの定義テーブルが多数含まれています。セクション指定でテーブルを抽出します。

```json
// get_tables({ section: "7.3.7" })
{
  "tables": [
    {
      "headers": ["Key", "Type", "Value"],
      "rows": [
        ["Type", "name", "(required) The type of PDF object..."],
        ["Length", "integer", "(required) The number of bytes..."]
      ]
    }
  ]
}
```

### 8. `compare_versions` — PDF 1.7 ↔ 2.0 の差分比較

PDF 1.7 と 2.0 の両方の仕様書がある場合、セクション構造の差分を比較できます。

```json
// compare_versions({ section: "12.8" })
{
  "matched": [
    { "pdf17": "12.8.1 General", "pdf20": "12.8.1 General", "status": "same" },
    { "pdf17": "12.8.2 ...",     "pdf20": "12.8.2 ...",     "status": "moved" }
  ],
  "added": ["12.8.3.3.2 PAdES signatures"],
  "removed": []
}
```

「PDF 2.0 で追加されたデジタル署名関連のセクションは？」— これは仕様書を2冊並べて読まないと答えられない質問ですが、このツールで即座に確認できます。

## 技術的な設計判断

### なぜ pdfjs-dist を選んだか

PDF解析ライブラリの選定で最初に候補に挙がったのは **mupdf**（MuPDFのJavaScriptバインディング）でした。テキスト抽出性能が高く、フォント名やサイズも取得できます。
:::message
しかし調査の結果、**pdfjs-dist**（Mozilla製）を採用しました。決め手は **Tagged PDF サポート** です。

ISO 32000-2 の仕様書PDF自体が Tagged PDF として作られており、内部にセマンティックな構造情報を持っています。pdfjs-dist の `page.getStructTree()` でこの構造ツリーにアクセスできます。
:::

```
実際の StructTree 出力:
<H3> "7.3.4 String objects"          ← セクション見出し
<H4> "7.3.4.1 General"              ← サブセクション
<P>  "A string object shall..."      ← 段落
<L>                                  ← リスト
  <LI> "• As a sequence of..."
<Table>                              ← テーブル
  <TR>
    <TH> "Sequence"
    <TD> "Meaning"
```

### これにより、一般的なPDF解析で必要な以下の処理が**不要**になります。

| 一般的なアプローチ | pdfjs-dist + Tagged PDF |
|---|---|
| フォントサイズで見出しを推定 | **H1-H6 タグで直接判別** |
| x座標クラスタリングでテーブル再構成 | **Table/TR/TH/TD で構造化済み** |
| y座標フィルタでヘッダー/フッター除外 | **Artifact タグで識別** |

フォントサイズによるヒューリスティクスは、ドキュメントによって閾値の調整が必要です。Tagged PDF の構造タグは一意に意味が決まっているので、堅牢に動作します。

```typescript
// pdfjs-dist の3つの重要API
const structTree = await page.getStructTree();      // セマンティック構造
const textContent = await page.getTextContent({
  includeMarkedContent: true                         // タグとテキストの紐付け
});
const styles = textContent.styles;                   // フォント種別（serif/monospace等）
```

**ライセンスの問題も重要でした。** mupdf は AGPL-3.0 で、利用条件が厳しい。pdfjs-dist は Apache-2.0 で MIT ライセンスの pdf-spec-mcp と問題なく組み合わせられます。

| | pdfjs-dist | mupdf |
|---|---|---|
| Tagged PDF 構造 | `getStructTree()` ✅ | なし（フォントで推定） |
| ライセンス | **Apache-2.0** | AGPL-3.0 |
| PDFロード時間 | 約150ms | 約80ms |

性能差はありますが、キャッシュすれば問題になりません。構造の正確さとライセンスの自由度を優先しました。

### 「読む」と「引く」の違い

汎用PDFリーダーは「このPDFのテキストを全部出して」という操作に最適化されています。セクション番号で引く、要件文だけ抽出する、テーブル構造を保持する — こうした操作は、仕様書の**構造を理解**していないとできません。

pdf-spec-mcp のアーキテクチャは、この「構造理解」を中心に設計しています。

```
PDF読み込み → アウトライン解析 → セクションインデックス構築
                                        ↓
                              セクション番号 → ページ範囲のマッピング
                                        ↓
                              指定ページの StructTree 解析
                                        ↓
                              型付きコンテンツ要素に変換
                              (heading / paragraph / table / list / note)
```

985セクションそれぞれに対して、開始ページ・終了ページが計算済みです。`get_section("12.8.3")` と呼ばれたとき、必要なページだけを処理するので、1,020ページ全体を解析する必要はありません。

## セットアップ

### 前提条件

- Node.js >= 20.0.0
- PDF仕様書ファイル（[PDF Association](https://pdfa.org/sponsored-standards/) から無料でダウンロード可能）

### インストール

Claude Desktop の場合、`claude_desktop_config.json` に追加

```json
{
  "mcpServers": {
    "pdf-spec": {
      "command": "npx",
      "args": ["-y", "@shuji-bonji/pdf-spec-mcp"],
      "env": {
        "PDF_SPEC_DIR": "/path/to/pdf-specs"
      }
    }
  }
}
```

`PDF_SPEC_DIR` に PDF仕様書を配置するだけで動きます。ファイル名パターンで自動的に文書を識別するので、設定ファイルは不要です。

Cursor / VS Code でも同様の設定で利用できます。

## まとめ

pdf-spec-mcp は「PDF仕様書をLLMの知識インフラに組み込む」ためのツールです。

- **PDF 2.0 の情報格差を埋める** — ネット上に情報が少ない PDF 2.0 の仕様を、LLM が直接参照できる
- **構造化されたアクセス** — 1,020ページの仕様書から必要なセクション・テーブル・要件だけを取得
- **Tagged PDF の活用** — pdfjs-dist の `getStructTree()` で、ヒューリスティクスに頼らない堅牢な構造解析
- **バージョン比較** — PDF 1.7 → 2.0 で何が変わったかを一目で確認

PDF仕様に限らず、Tagged PDF として作られた ISO 規格文書であれば、同様のアプローチが応用できる可能性があります。
