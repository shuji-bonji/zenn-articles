## はじめに

エージェントの統制（誰が実行したか、何を許すか、何を記録するか）が整うと、次に問われるのは「そのエージェントに任せてよい品質か」です。

ここでいう品質は、モデル単体の性能ではありません。指示・参照知識・ツール・判定コードをまとめた一式の品質です。

この記事は、その時期に向けて専門家エージェントを作り提供する側が、何を方針とし、何を測るかを先に定めておくためのものです。対象は、筆者が公開している PDF Agent Stack と Houki Hub を中心とする専門家エージェント群です。

https://shuji-bonji.github.io/pdf-agent-stack/ja/

https://shuji-bonji.github.io/houki-hub/

## エージェントへの ID 付与と内部統制

エージェントに ID を振るのは、これまで人や部署に行ってきた内部統制を、エージェントにも当てはめられるようにするためです。内部統制は「誰が」を特定できることを前提にしており、ID がなければ権限・承認・記録のどれも機能しません。

| 内部統制の要素 | 人に対して行ってきたこと | エージェントへの当てはめ |
| --- | --- | --- |
| 識別と認証 | 社員 ID、ログイン | エージェントごとの識別子と署名 |
| 職務分掌 | 申請者と承認者を分ける | 役割ごとに別のエージェントとして登録する |
| 最小権限 | 職務に必要な権限だけを付与する | エージェントごとのポリシーで使える操作を制限する |
| 承認 | 金額などに応じて決裁者を決める | 条件を満たす操作を人の承認に回す |
| 監査証跡 | 誰がいつ何をしたかの記録 | イベントと判定を記録し、署名付きの証明書を出力する |

ただし、人と同じ扱いでは足りない点があります。

- エージェントは法的な責任主体ではないため、ID は責任を負う人（所有者・運用者）まで必ずたどれるようにする。
- 同じエージェントを同時に多数起動できるため、エージェントの ID と実行（セッション）の ID を分けて記録する。
- モデルや指示の更新で、同じ ID のまま行動が変わるため、どの版で動いたかを記録する。
- 誤りを短時間で大量に繰り返せるため、事後の監査だけでなく実行前に止める仕組みが要る。

## 提供の形と、PDF Agent Stack・Houki Hub の現状

専門家エージェントの提供の形は、どの部品を提供者の手元に置き、どの部品を利用者の環境に渡すかで分かれます。

| 観点 | 形 1: API として提供 | 形 2: パッケージを配布 | 形 3: 指示は配布、知識は提供者が保持 |
| --- | --- | --- | --- |
| 利用者が受け取るもの | 結果だけ | エージェント一式 | 指示と、知識への接続 |
| 利用者のデータの行き先 | 提供者のサーバー | 利用者の環境から出ない | 問い合わせ内容だけが提供者に届く |
| 利用者側での統制 | 中身が見えない | 自分の統制下で動かせる | 参照先だけ外部 |

PDF Agent Stack と Houki Hub はどちらも形 2（パッケージを配布）です。当面はこの形を固めるのが目的に合っています。

一般論では専門家エージェントの価値の中心は「振る舞いの指示」と「参照元の知識」ですが、両 Family では参照元の知識を提供者が所有していません。

| 部品 | PDF Agent Stack | Houki Hub |
| --- | --- | --- |
| 参照元の知識 | ISO 32000 などの仕様書。再配布できず、利用者が入手したものを参照 | e-Gov 法令 API v2 と国税庁サイト。所有者は公的機関 |
| 提供者が作った価値 | 判定コード、構造の読み取り、手順 | 引き方、調査手順 |

提供者の価値は「判定はコード、説明は LLM」のコード部分と、知識の引き方・手順にあります。そのため「知識を提供者のサーバーに置いて守る」形 3 の利点は、そのままでは生じません。

形 1（API として提供）は両 Family とも選びません。PDF では機密文書を預かることになり、Houki では業法の論点が強く出るうえ、利用者が手元で再現して反論できるという外部検証の目的から遠ざかるためです。

## 統制の次に問われる精度と、型・版・実行の識別

統制が整うと、次は「そのエージェントに任せてよい品質か」が問われます。評価の対象はモデル単体ではなく、指示・参照知識・ツール・判定コードをまとめた一式です。

人の組織でも、権限と承認の仕組みを整えた後は、能力と実績の評価に関心が移ります。外部の専門家に委託するときの確認事項は、ほぼそのままエージェントにも当てはまります。

| 人の専門家で確認すること | エージェント一式で確認すること |
| --- | --- |
| 資格・専門分野 | 対応する領域と、扱わない業務の範囲 |
| 参照資料が最新か | 参照知識の基準日、法改正などへの追随 |
| 実績 | 版ごとの評価結果と運用実績 |
| 判断の根拠を示せるか | 出典を示すか、判定根拠を出力するか |
| 判断のぶれが小さいか | 同じ入力に同じ判定を返すか |
| 権限外の判断をしないか | 境界を守るか（判定を LLM が上書きしないか） |

### 識別は 3 段に分ける

エージェントは実行のたびに別のインスタンスが立ち上がり、前回の経験を引き継ぎません。そのため識別を型・版・実行の 3 段に分け、品質評価は版に付け、権限と記録は実行に付ける必要があります。

| 段 | 何を識別するか | 付けるもの |
| --- | --- | --- |
| 型 | エージェントの種類と業務範囲 | 役割、任せる業務の範囲 |
| 版 | 指示・知識の基準日・モデル・判定コードの組み合わせ | 品質評価、信頼。どれか 1 つが変われば再評価 |
| 実行 | 個々のセッション | 権限、監査記録。記録には「どの版で動いたか」を含める |

型の下に版があり、品質評価は版に付きます。実行は毎回新しく作られ、権限と監査記録が付き、その記録にはどの版で動いたかを残します。

外部の資料は、実行の識別と、知識層が精度を決めることを別々に論じています。両者をつなぐ版の段は、確認した範囲では明示されていませんでした。ここがこの方針の独自性を置く場所です。

この構造は人の資格制度よりも、工業製品の型式認証に近いものです。型式（設計と版）を審査して認め、個々の製品（実行）は製造番号で追跡します。人の資格は一度取れば有効なままですが、エージェントの評価は版に付くため、モデルの更新や知識の差し替えで失効します。

## 予想される認証・認定制度

専門家エージェントの需要が増えると、1 つの制度ではなく、対象の違う複数の認証が重なる形になると予想します（推測を含みます）。中心になるのは「版の型式認証」と「変更計画の事前承認」です。

| 制度 | 対象 | 確かめること | 似ている既存の制度 |
| --- | --- | --- | --- |
| 組織の認証 | 提供・運用する組織 | 統制の仕組み、記録、責任者の体制 | ISO/IEC 42001、ISMS |
| 参照知識の認証 | 知識の提供元・データセット | 出典が一次情報か、基準日、更新頻度 | 統計データ・地図データの品質認証 |
| 判定部品の認証 | 判定コード、検証器 | 同じ入力に同じ結果を返すか | 計量器の検定、veraPDF |
| 版の型式認証 | エージェント一式の特定の版 | 業務範囲、非公開の試験での精度、境界の遵守 | 工業製品の型式認証 |
| 変更計画の事前承認 | 版の更新方法 | どの範囲の変更なら差分試験だけで済むか | 医療機器ソフトウェアの変更管理計画 |
| 運用中の継続監視 | 認定済みの版の運用 | 誤り率、差し戻し率、不具合の報告 | 市販後調査 |
| 業務での利用認定 | 士業・業界での使い方 | 有資格者の監督の下でどの補助業務に使えるか | 士業団体の指針 |

人の資格制度との違いは 3 点です。

- 有効期間は版が変わるまで。モデルの更新や知識の差し替えで失効する。
- 実績の引き継ぎは、新しい版が前の版と同じ判定を返すことを確かめた範囲（版間一致率）でだけ可能。
- 見るものは能力に加えて、仕様どおりに振る舞うか（出典を示すか、境界を守るか、判定がぶれないか）。

試験問題が公開されていると、その問題に合わせて調整できてしまうため、型式試験の問題は非公開で入れ替えられるはずです。法律など独占業務のある領域では、エージェントは評価が高くても有資格者の補助者にとどまり、認定の内容も「補助業務の範囲で一定の水準を満たす」という形になります。

認定を出す主体は危険度で分かれ、高い領域（医療、与信、採用、行政の判断）は規制当局、中程度の領域（法務・税務・労務の補助、技術審査）は業界団体や士業団体、低い領域はマーケットプレイスの審査や自己宣言になると考えます。法律で義務付けられる前に、保険と大企業の調達基準が事実上の基準として先に広まる、という順序を予想します。

## 方針と指標

将来の認証・認定制度の細部が決まる前から、どの制度でも求められる要件を作る段階で満たしておくことを目的とします。制度ができてから合わせるのではなく、版を固定し、指標を宣言し、記録を残す習慣を先に持ちます。

### 基本方針

1. 利用者の環境で動かす。提供形態は形 2（パッケージを配布）を基本とする。
2. 判定はコード、説明は LLM。最終判定はルールエンジンや外部検証器が出し、LLM は判定を上書きしない。
3. 品質は版に付ける。指示・知識の基準日・モデル・判定コードの組み合わせを版として固定し、評価結果はその版に記録する。
4. 実行の記録に版を残す。出力する報告書には、どの版で動いたかを必ず含める。
5. 業務範囲を宣言する。するとしないことを明記し、業法の独占業務には踏み込まない。
6. 指標を先に宣言する。Family ごとに指標と目標を作る前に書き、実測値を版ごとに更新する。
7. 未計測を未計測と書く。外部の利用者がいない段階の運用実績は自己運用の記録として区別し、外部の実績と混ぜない。
8. 形 1（API として提供）は選ばない。

### 品質指標の 5 分類

| 分類 | 内容 | 測る時期 | 想定される認定制度 |
| --- | --- | --- | --- |
| 能力評価 | 所定の課題セットで、一定の正確さと網羅性を満たす | リリース前 | 版の型式認証 |
| 制約遵守 | 許可されていない操作をしない、出典を明示する、判定を上書きしない | リリース前、運用中 | 版の型式認証、業務での利用認定 |
| 再現性・一貫性 | 同じ入力に同じ判定を返す。版を上げても既知事例の判定が意図せず変わらない | リリース前、更新時 | 変更計画の事前承認 |
| 運用実績 | 本番での成功率、人間による修正率 | 運用中 | 運用中の継続監視、保険の引受条件 |
| 鮮度管理 | 参照知識の基準日と更新頻度 | 知識の更新時 | 参照知識の認証 |

Judgment 適格度に合わせます。判定をコードで行う Family（PDF）は判定の正しさと再現性を中心にし、判定を LLM に委ねる Family（Houki）は引用の正確さと境界の遵守を中心にします。判定精度を求めないこと自体を宣言に含めます。

## おわりに

エージェントの統制が整った後、専門家エージェントのニーズが増えると予想されます。そのときに問われるのは、モデル単体の性能ではなく、指示・参照知識・ツール・判定コードをまとめた一式の品質です。

この品質を測り、示すための単位として、型・版・実行の 3 段を提案しました。品質評価は版に付け、権限と記録は実行に付けます。

この区別は、人の資格制度よりも工業製品の型式認証に近いものです。制度ができる前から、版を固定し、指標を宣言し、記録を残す習慣を持っておくことが、準備の中心になります。

本稿の内容は、専門家エージェント作成ガイド v2 を補う方針として整理しています。実装の詳細は各 Family のリポジトリを参照してください。
