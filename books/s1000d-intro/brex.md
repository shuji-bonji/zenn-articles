---
title: "BREX とビジネスルール"
---

S1000D は、すべてのプロジェクトに同じ細かいルールを求める仕様ではありません。スキーマが認める書き方の中から、プロジェクトがさらにルールを選びます。そのルールを人が読む文書にまとめたものがビジネスルールで、そのうち XML の構造の使い方に関するものを、機械で検査できるデータモジュール（DM）にしたものが BREX（Business Rules Exchange）です。

この章では、仕様とプロジェクトのルールの境界と、BREX の役割を説明します。BREX のスキーマの要素や、検査の式（XPath）の書き方は扱いません。

## 仕様とプロジェクトのルールの境界

境界は、次の三つの層に分けると分かりやすくなります。

| 層 | 何を決めるか | どこに書かれるか |
| --- | --- | --- |
| 仕様 | DM という単位、DMC という識別、CSDB という保管、種類ごとのスキーマの枠 | 使う版の仕様書とスキーマ |
| プロジェクトのビジネスルール | 仕様の枠の中で、このプロジェクトがどれを使い、どの値を許し、何を必須にするか | 人が読むルールの文書。版によっては、決めるべき点の一覧（Business Rules Decision Point、BRDP の索引）が仕様に同梱される |
| BREX | 上のルールのうち、XML の構造について機械で検査できるもの | 情報コード `022` の DM。CSDB に保管し、ほかの DM から参照する |

スキーマを満たす XML は、その版のスキーマに対して正しい XML です。しかし、スキーマを満たすことと、プロジェクトのルールを満たすことは別です。たとえば、スキーマがリストの項目を 1 個から認めていても、プロジェクトは 2 個以上を必須にできます。これは仕様の改訂ではなく、プロジェクトのルールです。逆に、プロジェクトで便利な運用を、仕様の要求であるかのように書かないことも大切です。

### 決めるべき点の一覧

仕様のパッケージには、プロジェクトが決めるべき点の一覧が同梱されています。名前は版によって違います。

| 版 | 一覧の名前 |
| --- | --- |
| Issue 4.1 | Business Rule Decision Point index（ダウンロードの説明による） |
| Issue 5.0 | Project Decision Point Index（ダウンロードの説明による） |
| Issue 6 | `S1000D Issue 6 BRDP Index.xlsx` |
| Issue 7 | `S1000D Issue 7 BRDP Index.xlsx` |

どの版でも、既定の BREX と一緒に同梱されています。この一覧に沿って決めた結果が、そのプロジェクトのビジネスルールです。

### ルールの層

Issue 7 の第2.5.1章は、ビジネスルールの層を、ルールが適用される関係者の階層として説明しています。一番上の層の中心は、常に S1000D 自身です。その下の層の数は、組織とプロジェクトの構造によって変わります。同じ章は、例として、防衛の 6 層と、民間航空の 3 層を図で示しています。下の層は上の層のルールを引き継ぎ、まだ決まっていない点のうち、自分の層で決めるものを決めます。プロジェクトは、自分の層に決めるべき点を追加することもできます。

## BREX は DM の一種

[公式の概要ページ](https://s1000d.org/?page_id=101)は、Business Rules Exchange を DM の種類の一つとして挙げています。BREX は、仕様とは別の形式のファイルではなく、DM そのものです。ほかの DM と同じように、識別・状態の部分と内容の部分を持ち、DMC を持ち、CSDB に保管します。

### 既定の BREX

仕様の各版のパッケージには、その版が最初から持っている規則をまとめた既定の BREX が同梱されています。Issue 7 の既定 BREX の DMC は `S1000D-J-04-10-0301-00A-022A-D`、`infoName` は “Business rules exchange”、`issueDate` は 2026-07-16 です。

既定 BREX の DMC は、版によってシステム差分コードが違います。Issue 4.2 の複製では `F`、Issue 6 では `H`、Issue 7 では `J` で、それ以外の属性は同じです。情報コードはどれも `022`、アイテムロケーションコードはどれも `D` で、この二つの値は Issue 6 と Issue 7 の第4.10.2.4章にも書かれています。三つのファイルの詳しい比較は、[付録](https://zenn.dev/shuji_bonji/books/s1000d-intro/viewer/package-notes)にまとめています。

Issue 7 の第4.10.3章は、既定 BREX が、設定できる属性の値、使える情報コード、使える学習コード、スキーマでは表せない規則を定めていると説明しています。そのうえで、プロジェクトや組織は、既定 BREX が自分たちの要求に合っているかを検討する、と書いています。既定 BREX は、そのままプロジェクトの BREX として納品するものではありません。

### プロジェクトの BREX

プロジェクトの BREX は、プロジェクトが規則を追加して、関係者とやり取りするための DM です。プロジェクトの DM は、識別・状態の部分で、どの BREX に従って検査されるかを参照します。

参照に使う要素名は、版によって違います。

| 版 | 参照の書き方 |
| --- | --- |
| Issue 3.0 | DM の `brexref` |
| Issue 4.0 | DM の `brexDmRef`。PM のスキーマ（`pm.xsd`）には `brexDmRef` がない |
| Issue 4.1 以降 | DM に加えて、PM も `brexDmRef` を持つ |

この表は、各版の自転車サンプルと、Issue 4.0 の `pm.xsd` で確認したものです。使う版のスキーマで確認してください。

プロジェクトの BREX が組織の BREX を参照し、組織の BREX が仕様の既定 BREX を参照する、というように重ねて使うこともあります。層の数は、Issue 7 の第2.5.1章のとおり、組織によって違います。契約に「プロジェクト BREX を納品する」とあれば、既定 BREX の複製ではなく、そのプロジェクトで決めた規則を含む DM を納品します。

自転車サンプルにも、プロジェクト用の BREX（モデル識別コード `S1000DBIKE`、情報コード `022`、`techName` は “Mountain bicycle”）があります。これは、モデル識別コード `S1000D` の既定 BREX とは別の DM です。Issue 6 のサンプルのプロジェクト用 BREX は Issue 6 の既定 BREX（`H`）を、Issue 7 のサンプルのものは Issue 7 の既定 BREX（`J`）を参照しています。

:::message
パッケージの中には、仕様本文とファイルが食い違っている箇所もあります。たとえば、第4.10.2.4章は BREX のアセンブリコードを `00` または `0000` としていますが、既定 BREX の `assyCode` は `0301` です。また、Issue 7 のビジネスルールのテンプレートは、Issue 7 の既定 BREX（`J`）ではなく、Issue 6 の既定 BREX と同じ `H` を参照しています。プロジェクトの BREX を作るときは、その版の章と、参照する既定 BREX の両方を確認し、参照先はファイルに書かれた DMC で確かめてください。詳しくは付録にまとめています。
:::

## BREX が扱うものと扱わないもの

BREX が扱うのは、機械で検査できる規則です。Issue 4.2 の既定 BREX を見ると、使える情報コード、SNS の使い方、特定の要素を必須にするかどうか、といった規則が、仕様の章を参照しながら並んでいます。プロジェクトの BREX も、同じ形でプロジェクトの値を決めます。たとえば、モデル識別コードに何を使うか、アセンブリコードを 2 文字にするか 4 文字にするか、です。[第5章](https://zenn.dev/shuji_bonji/books/s1000d-intro/viewer/data-module-code)で見た桁数の違いは、この層で決まります。

一方、次のものは BREX では扱いません。

- 画面のレイアウトや、ビューアの製品の選定
- 執筆の担当の分担、納期、承認の会議
- 仕様のスキーマ自体の変更（CPF で扱うもので、プロジェクトの BREX ではできない）
- 検査の式にできない規則（人が読むビジネスルールの文書に残す）

### 人が読むビジネスルール

Issue 6 と Issue 7 のパッケージには、人が読むビジネスルールのテンプレートが同梱されています。情報コードは `024`、`infoName` は “Business rules”、スキーマは `brdoc.xsd` です（Issue 7 の DMC は `S1000D-J-04-10-0100-00A-024A-D`）。人が読む規則と、機械が検査する規則を分けるという考え方は、このテンプレートと既定 BREX が別の DM になっていることに表れています。テンプレートの詳細は付録にまとめています。

## BREX の読み始め方

BREX のファイルを最初から最後まで読む必要はありません。次の順で読めば十分です。

1. 使う版の既定 BREX の DMC と標題を確認し、それが仕様側の既定の BREX であることを把握する。
2. プロジェクトの BREX があるかを、契約と納品物の一覧で確認する。
3. プロジェクトの DM が、どの BREX を参照しているかを、識別・状態の部分で確認する。
4. 情報コードと SNS について、プロジェクトが許している値だけを読む。
5. 個々の要素の必須や禁止は、その要素を書くときに参照する。

多くの実装では、まずスキーマで検査し、通った XML をさらに BREX で検査する、という二段階の検査をしています。ただし、二段階にすること自体は、仕様の概要ページに書かれているわけではありません。正しい XML を、さらにプロジェクトのルールに照らして検査できるようにするのが BREX の目的です。

:::message
BREX の仕組みの範囲は、BREX をやり取りし、参照し、検査に使うことまでです。仕様は、特定の検査ツールの導入を求めていません。どの製品で検査するかは、プロジェクトが決めます。
:::

## この章のポイント

- 仕様が定める枠と、プロジェクトが追加するルールは、別の層です。BREX は、プロジェクトのルールのうち XML の構造に関する部分を、機械で検査できる DM にしたものです。
- 各版のパッケージには既定の BREX が同梱されています。プロジェクトの BREX は、その複製ではなく、プロジェクトで決めた値を持つ DM です。
- BREX の情報コードは `022`、アイテムロケーションコードは `D` です。既定 BREX のシステム差分コードは版によって違い、BREX を参照する要素名も版によって変わります。
