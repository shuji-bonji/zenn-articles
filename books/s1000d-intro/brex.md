---
title: "BREX とビジネスルール"
---

S1000D は、すべてのプロジェクトが同じ詳細ルールで書く仕様ではありません。スキーマが許す書き方の中から、プロジェクトがさらにルールを選びます。そのルールを、人が読む文書として残すものがビジネスルールです。そのうち、XML の構造の使い方に関するものを、機械が読める DM として交換するものが BREX（Business Rules Exchange）です。

この章は、その境界を説明します。BREX のスキーマの中の要素や、XPath の書き方には入りません。

## 仕様とプロジェクトのルール

境界は、次の三層です。

| 層 | 何を決めるか | どこに書かれるか |
| --- | --- | --- |
| 仕様 | DM という単位、DMC という識別、CSDB という保管、種類ごとのスキーマの枠 | 入手した Issue の仕様書とスキーマ |
| プロジェクトのビジネスルール | その枠の中で、このプロジェクトがどれを使い、どの値を許し、何を必須にするか | 人が読むルール文書。決定の一覧として、版によっては Business Rules Decision Point（BRDP）の索引が同梱される |
| BREX | 上のルールのうち、XML の構造に関して機械が検査できるもの | 情報コード `022` の DM。CSDB に保管し、他の DM から参照する |

スキーマを満たす XML は、その版のスキーマに対して妥当です。妥当であることと、プロジェクトのルールを満たすことは別です。スキーマがリストを1項目から許していても、プロジェクトは2項目以上を必須にできます。その追加は仕様の改訂ではなく、プロジェクトのルールです。逆に、プロジェクトの便利な運用を、仕様の要求であるように書かない、というのも同じ境界です。

Issue 4.1 のダウンロード説明は、パッケージに Default BREX module と Business Rule Decision Point index が含まれると書いています。Issue 5.0 の説明は、Default BREX module と Project Decision Point Index という名前で対応する同梱物を挙げています。Issue 6 のパッケージは、既定 BREX の ZIP と、`S1000D Issue 6 BRDP Index.xlsx` を別ファイルとして含みます。Issue 7 のパッケージは、既定 BREX の ZIP と、`S1000D Issue 7 BRDP Index.xlsx` を別ファイルとして含みます。索引の名称は版で違います。役割は、プロジェクトが決めるべき点を仕様が列挙している、ということです。決めた結果が、そのプロジェクトのビジネスルールです。

Issue 7 の第2.5.1章は、ビジネスルールの層を、その規則が適用される関係者の階層だと定義しています。最上の層の核は常に S1000D 自身です。それより下の層の数は、組織とプロジェクトの構造で変わります。同じ章が図で示している例は、防衛の六層と、民間航空の三層です。六層は例であり、すべてのプロジェクトの層の数ではありません。下の層は上の層を継承し、残っている決定点のうち自層で決めるものを決めます。プロジェクトは、自層に決定点を追加することもできます。

## BREX は DM である

公式の概要は、Business Rules Exchange を情報の種類の一つに挙げています。BREX は、仕様の外にある別形式のファイルではありません。DM です。識別・状態の部分と内容の部分を持ち、DMC を持ち、CSDB に保管します。

Issue 4.2 として流通している既定 BREX の標題は “Default business rules exchange data module” です。方針文は “S1000D at Issue 4.2” です。DMC は `S1000D-F-04-10-0301-00A-022A-D` です。このファイルは公式パッケージの複製です。

Issue 6 のパッケージに同梱されている既定 BREX の DMC は `S1000D-H-04-10-0301-00A-022A-D` です。ファイル名は `DMC-S1000D-H-04-10-0301-00A-022A-D_001-00_EN-US.XML`、`infoName` は “Business rules exchange”、方針文は “S1000D-SC-2016-017-002-00 Steering Committee TOR”、`issueDate` は 2024-06-19、発行番号は `001`、作業中番号は `00` です。スキーマの宣言は `http://www.s1000d.org/S1000D_6/xml_schema_flat/brex.xsd` です。この URL を、本書の執筆時に再取得してはいません。`systemDiffCode` は `H` です。自分自身を `H` として参照しています。ファイルは、情報コード `022` とアイテムロケーションコード `D` を、Chap 4.10.2.4 Para 2 として検査しています。Issue 6 の第4.10.2.4章の本文も、情報コードは `022`、アイテムロケーションコードは `D` と書いています。

Issue 7 のパッケージに同梱されている既定 BREX の DMC は `S1000D-J-04-10-0301-00A-022A-D` です。`infoName` は “Business rules exchange”、方針文は “S1000D-SC-2016-017-002-00 Steering Committee TOR”、`issueDate` は 2026-07-16 です。`systemDiffCode` は `J` です。自分自身を `J` として参照しています。`H` でも、Issue 4.2 の複製の `F` でもありません。`systemDiffCode` 以外の `dmCode` の属性は、Issue 4.2 の複製、Issue 6 の同梱ファイル、Issue 7 の同梱ファイルで同じです。Issue 6 と Issue 7 のファイルは、どちらも情報コード `022` とアイテムロケーションコード `D` を Chap 4.10.2.4 として検査しています。Issue 7 の第4.10.2.4章の本文も、同じ二つの値を書いています。第4.10.3章は、既定 BREX が、設定可能な属性の値、許される情報コード、許される学習コード、スキーマに直接書けない規則を定める、と書いています。プロジェクトまたは組織は、それが要求に合うかを検討する、とも書いています。既定 BREX を、プロジェクトの BREX の完成品として納品しません。

:::message alert
Issue 6 の第4.10.2.4章は、SNS をサブサブシステムより下には適用しない、と書き、BREX のアセンブリコードを `00` または `0000` とする、とも書いています。同じパッケージの既定 BREX の `assyCode` は `0301` です。Issue 7 の第4.10.2.4章も、アセンブリコードを `00` または `0000` とし、同梱の既定 BREX の `assyCode` は `0301` です。本書はこの差を、どちらかが誤記だと決めて解消しません。
:::

:::message
Issue 6 の既定 BREX として上に書いたのは、パッケージ本体の発行番号 `001`、日付 2024-06-19 のファイルです。同じパッケージの `S1000D Issue 6 Patches.zip` の中にも、同じ DMC の後の発行があります。ディレクトリ `S1000D_6.A_ BREX` のファイルは発行番号 `002`、作業中番号 `00`、日付 2025-10-26 です。データ辞書のパッチ側のファイルは、ファイル名が `_002-01` で、識別子は発行番号 `002`、作業中番号 `01`、日付 2025-09-05 です。本体の `001` を、パッチの発行に置き換えて読みません。二つの後の発行も、一つにまとめません。
:::

既定の BREX は、その Issue が最初から持っている規則の集合です。プロジェクトの BREX は、プロジェクトが追加し、交換するための DM です。プロジェクトの DM は、どの BREX に対して検査されるかを、識別・状態の部分の参照で示します。参照の要素名は版で違います。公開の検証手順の説明では、Issue 3.0 では DM に `brexref`、Issue 4.0 では DM に `brexDmRef`、Issue 4.1 以降は DM に加えて PM など他の CSDB オブジェクトにも `brexDmRef` が要る、と書かれています。名前は、対象の版のスキーマで確認します。

プロジェクトの BREX が、組織の BREX を参照し、組織の BREX が仕様の既定 BREX を参照する、という重ね方をすることがあります。層の数は、上に書いた Issue 7 の第2.5.1章のとおり、組織ごとに違います。契約に「プロジェクト BREX を納品する」とあれば、納品物は既定 BREX の複製ではなく、そのプロジェクトが決めた規則を含む DM です。既定 BREX への参照を含むかどうかは、その版の規則に従います。

Issue 6 の自転車サンプルには、モデル識別 `S1000DBIKE`、情報コード `022` のプロジェクト用 BREX があります。ファイルの発行番号は `011`、`issueDate` は 2024-06-19、`techName` は “Mountain bicycle” です。このプロジェクト用 BREX の `brexDmRef` は、Issue 6 の既定 BREX の `systemDiffCode` `H` を指しています。Issue 7 の自転車サンプルにも、同じモデル識別と情報コードのプロジェクト用 BREX があります。`techName` は “Mountain bicycle” です。これは、モデル識別 `S1000D` の既定 BREX とは別の DM です。Issue 7 のプロジェクト用 BREX の `brexDmRef` は、Issue 7 の既定 BREX の `systemDiffCode` `J` を指しています。

:::message alert
Issue 7 のビジネスルールのテンプレート（情報コード `024`、DMC は `S1000D-J-04-10-0100-00A-024A-D`）の `brexDmRef` は、`systemDiffCode` が `H`、アセンブリ `0301`、情報コード `022`、アイテムロケーション `D` の BREX を指しています。この並びは、Issue 6 の既定 BREX の DMC `S1000D-H-04-10-0301-00A-022A-D` と一致します。Issue 7 の既定 BREX 自身の `systemDiffCode` は `J` で、自分自身を `J` として参照しています。Issue 7 のテンプレートは、同じパッケージの `J` を指していません。本書は、この参照を `J` に読み替えません。参照先は、ファイルに書いてある DMC で確認します。
:::

## BREX が運ぶものと、運ばないもの

BREX が運ぶのは、機械が検査できる規則です。Issue 4.2 の既定 BREX の中身を見ると、許される情報コード、SNS の使い方、特定の要素を必須にするかどうか、といった規則が、仕様の章を参照しながら並んでいます。プロジェクトの BREX も、同じ役割をプロジェクトの値で埋めます。たとえば、モデル識別コードとして何を許すか、アセンブリの桁を2文字にするか4文字にするか、です。第5章で見た桁の違いは、この層で決まります。

BREX が運ばないものもあります。

- 画面のレイアウトや、ビューアの製品の選定
- 執筆の担当分け、納期、承認の会議体
- 仕様のスキーマそのものの改訂。それは CPF の対象であり、プロジェクトの BREX では行えない
- 人が読む説明のすべて。検査用の式にできない規則は、ビジネスルール文書の側に残ります

Issue 6 と Issue 7 のパッケージには、人が読むビジネスルールのテンプレートがあります。Issue 6 の XML の DMC は `S1000D-H-04-10-0100-00A-024A-D`、`infoName` は “Business rules”、`assyCode` は `0100`、スキーマの宣言は `brdoc.xsd`、`issueDate` は 2024-06-19 です。識別子の発行番号は `001`、作業中番号は `00` です。ファイル名は `DMC-S1000D-H-04-10-0100-00A-024A-D_000-01_EN-US.xml` です。ファイル名の `000-01` と、識別子の `001`/`00` を、どちらかに揃えて読み替えません。`brexDmRef` は、Issue 6 の既定 BREX の `H` を指しています。同じ ZIP には `DMC-S1000D-H-04-10-0102-00A-024A-D_001-00_EN-US.PDF` もあります。アセンブリが `0102` であり、`0100` の XML とは別の DMC です。この PDF の本文は、本書の記述には使っていません。

Issue 7 のテンプレートの DMC は `S1000D-J-04-10-0100-00A-024A-D`、`infoName` は “Business rules”、`assyCode` は `0100`、スキーマの宣言は `brdoc.xsd`、`issueDate` は 2026-07-16 です。情報コード `024` は、Issue 6 と Issue 7 のこのテンプレートで確認した、人が読む規則の DM です。それより前のすべての版に同じ種類があるとは、本書では確認していません。人が読む規則と、機械が検査する規則を分ける、という考え方は、このテンプレートと既定 BREX が別ファイルであることに現れています。要素名は対象の版で確認します。

## 読み始めるときの順序

BREX のファイルを最初から最後まで読む必要はありません。次の順で足ります。

1. 対象の Issue の既定 BREX の DMC と標題を確認し、それが「仕様側の既定」だと分かるようにする。
2. プロジェクトの BREX があるか、契約と納品物の一覧で確認する。
3. プロジェクトの DM が、どの BREX を参照しているかを、識別・状態の部分で見る。
4. 情報コードと SNS の、プロジェクトが許す値だけを読む。
5. 個別の要素の必須・禁止は、その要素を書くときに参照する。

スキーマ検査を通ったあとに BREX 検査がある、という二段は、多くの実装が採用しています。二段であること自体は、仕様の概要ページの文ではありません。妥当な XML を、プロジェクトのルールに対しても検査できるよう BREX がある、という目的の範囲で理解すれば足ります。

:::message
BREX を交換し、参照し、検査に使う、というのがこの仕組みの範囲です。特定の検査ツールの導入を、仕様が要求しているわけではありません。検査をどの製品で行うかは、プロジェクトが決めます。
:::

## この章のポイント

- 仕様が定める枠と、プロジェクトが追加するルールは別の層である。BREX は、後者のうち XML の構造に関する部分を、機械可読な DM として交換する仕組みである。
- 各 Issue には既定の BREX が同梱される。プロジェクトの BREX は、その複製ではなく、プロジェクトが決めた値を持つ DM である。
- 既定 BREX の `systemDiffCode` は、Issue 4.2 の複製では `F`、Issue 6 の同梱ファイルでは `H`、Issue 7 の同梱ファイルでは `J` である。情報コード `022` とアイテムロケーションコード `D` は、これらのファイルと、Issue 6 および Issue 7 の第4.10.2.4章が書いている。参照の要素名は版で変わる。Issue 7 の情報コード `024` のテンプレートは、`J` ではなく Issue 6 の既定 BREX の DMC を参照している。
