---
title: "IETM と IETP の構成要素"
---

この章では、対話型電子技術マニュアル（Interactive Electronic Technical Manual、IETM）または対話型電子技術出版物（Interactive Electronic Technical Publication、IETP）を、どの構成要素が支えているかを整理します。S1000D に沿う場合を主に書きます。S1000D はデータの仕様であり、オーサリング製品やビューア製品を指定しません。

構成は、情報を作る場所、情報を管理する場所、情報を人に出す場所の三つに分かれます。

| 構成要素 | 役割 | 仕様が決めること |
| --- | --- | --- |
| オーサリング環境 | データモジュール（Data Module、DM）と図を作る | 出来上がる XML がスキーマと、事業が採用するビジネスルール交換（Business Rules Exchange、BREX）に合うこと。編集ソフトの製品名は決めない |
| 共通ソースデータベース（Common Source Data Base、CSDB） | DM、図、パブリケーションモジュール（Publication Module、PM）を保持し管理する | 保持と管理が必要であること。製品の機能は定義しない、と公式サイトが明記している |
| ビューア | PM と DM から、利用者の画面を作る | S1000D は IETP の機能を機能マトリックスで指定できる。ビューアのソフトウェアは仕様に同梱されない |

米国の MIL-PRF-87268A は、IETM 本体の内容と、それを出す電子表示装置（Electronic Display System、EDS）の利用者インタフェースの両方に要求を置いていました。S1000D は、データの側を共通化し、画面の必須機能は事業がマトリックスで選ぶ、という分け方です。

## オーサリング環境

書き手は、冊子の章を一続きで書くのではなく、DM を一つずつ作ります。一つの DM は識別・状態の部分と内容の部分を持ち、データモジュールコード（Data Module Code、DMC）で識別されます。説明、手順、図解部品、故障は、種類の違う DM です。

オーサリング環境に期待されるのは、XML を編集できること、DMC や適用情報を欠かさず入れられること、図を DM の外のオブジェクトとして参照できることです。検査は、採用する版の XML スキーマと、その DM が参照する BREX に対して行います。スキーマは仕様が許す形を決め、BREX は事業が選んだより狭い規則を決めます。事業が CSDB へ正式に受け入れる条件は、通常この二つの検査です。検査の前に一時的な置き場を禁じる、とまでは公式の概要ページは述べていません。

S1000D の公式サイトは、準拠したオーサリングツールが複数の供給者から得られることを、利点の一つに挙げています。特定の製品を公式が推奨しているわけではありません。

## CSDB

CSDB は格納場所の名前です。公式サイトは、機能を定義しない、と書いています。事業に必要なのは、作られた DM を保持し、DMC で取り出せ、版と適用と品質保証の状態を管理できることです。

ワークフロー、アクセス権、他システムとの接続は、仕様の外で事業が決めます。同じ S1000D のデータでも、CSDB 製品が違えば操作画面は違います。交換の対象は、製品の画面ではなく、DM と PM と図です。

## ビューア

ビューアは、CSDB の内容を、整備技術者や操作者の画面にします。S1000D の用語では、この画面向けの成果物が IETP です。米軍の文書ではほぼ相当する語が IETM です。

ビューアが行うことを、確認できた仕様の範囲で言うと次のとおりです。

- PM が示す構成に従い、参照先の DM を集める。
- 識別・状態の部分にある適用情報と、利用者の装備構成を突き合わせ、該当しない DM を出さない。公式の利点ページは、適用による絞り込みを利点に挙げている。
- 事業が機能マトリックスで選んだ機能（検索、印刷、注釈、外部システムとの接続など）を提供する。S1000D のマトリックスは、IETP だけでなくページ指向の出版物の機能も指定できる、と米空軍の MIL-STD-3048A が定義している。

MIL-PRF-87268A が規定したダイアログ、つまり質問に答えるまで次へ進まず、答えに応じて次の手順が変わる、という動作は、ビューアと、手順 DM の中に著者が書いた分岐の両方があって成立します。データが分岐を持たなければ、ビューアだけでは対話型になりません。

## データの流れ

:::message
下の図は論理的な流れです。検査をオーサリング環境が行うのか CSDB が行うのか、発行物を CSDB の外へ書き出すのかビューアが CSDB を直接読むのかは、仕様が一つの製品構成として固定していません。
:::

```mermaid
flowchart TB
  A["オーサリング環境<br/>DM と図を作成"] --> V["スキーマと BREX で検査"]
  V --> C["CSDB<br/>DMC で管理"]
  C --> P["PM が出版物の構成を定義"]
  P --> R["発行<br/>IETP 用データ、または紙・PDF"]
  R --> U["ビューア"]
  Q["利用者の装備構成・作業・症状"] --> U
  U --> T["技術者が見る画面<br/>該当する手順・説明・図"]
```

流れを文章にすると、次のとおりです。

1. 書き手が DM と図を作る。識別・状態には DMC、適用、BREX への参照が入る。
2. スキーマと BREX で検査し、CSDB に格納する。
3. PM が、どの DM をどの順序と階層で出版物に含めるかを定義する。技術内容は PM にはコピーしない。
4. 発行の処理が、IETP 用のデータ、またはページ指向の出力を作る。メジャー版の違いをまたぐ変換は、公式のダウンロード説明によれば人手の介在が要る。
5. ビューアが、利用者の装備、作業、症状に合わせて DM を選び、画面を組む。

## 仕様が構成要素にしないもの

S1000D の公式サイトは、CSDB の機能を定義しないと明記しています。ビューアの実行プログラムも、仕様のダウンロード物（仕様書、スキーマ、サンプル、既定の BREX、機能マトリックス）には含まれません。MIL-HDBK-511 が扱うのは、ブラウザを共通の入口にして異なる IETM を利用者が辿れるようにする相互運用であり、S1000D の CSDB の製品仕様ではありません。

:::message alert
「S1000D に準拠した」という説明は、データが仕様と事業の BREX に合っていることを意味し得ます。オーサリング環境、CSDB、ビューアの三つが同じ製品であることも、画面の操作が他事業と同じであることも、意味しません。画面の必須機能は、機能マトリックスの選択結果を契約に含めて初めて決まります。
:::

## この章のポイント

- 構成要素は、オーサリング環境、CSDB、ビューアの三つである。仕様が製品として定めているのは、このうちのどれでもない。
- データは DM として作られ、スキーマと BREX で検査され、CSDB に入り、PM が出版物の形を決める。
- 技術者が見る画面は、ビューアが装備・作業・症状に合わせて DM を選んだ結果である。どの機能が必須かは、機能マトリックスの選択で決まる。
